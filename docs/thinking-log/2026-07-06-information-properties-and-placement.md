---

## 出発点の素朴な問い

Plan・Review・README・GitHub のどこに、どの情報を置くのが正しいのか。
最初は **「更新頻度」** で分ければよいと考えた（不変 / 揮発 / スナップショット）。

## 思考の発展（軌跡）

1. **更新頻度だけでは足りなかった。** 「Plan / Review は一次情報っぽいが、実際には GitHub 上にあるべき
   内容が多い」という気づき。例: **レビューは GitHub 上でやるほうが機能する**（コメント・対応・解決・承認）。
   → 情報の性質だけでなく **媒体（ツール）の性質** と **作業モード**（Claude 完結か GitHub 連携か）も効く。
   Claude で完結させたいときは、むしろ GitHub を絡めないほうがよい場合もある。

2. **「インタラクション要否」を軸に足そうとしたが、曖昧だった。** これは 2 つに割れる:
   - **生成時**インタラクション（情報が*作られる過程*が対話的か）
   - **事後**インタラクション（確定した*後*にアクションが続くか）

3. **「事後インタラクション」の正体を突き詰めると「状態機械を持つか」だった。**
   残課題（TODO）を例にすると: 生成イベントとしては一方向（書き出すだけ）だが、
   時間的性質としては `open → done` という**ライフサイクル（状態機械）を内包**している。
   「事後にアクションが発生する」のは結果で、原因は*その情報が状態を保持し、いずれ遷移する運命*にあること。

4. **イベント視点と状態視点は直交する 2 軸だと分かった。**
   - 生成様式（イベント視点）: 一方向 / 対話的 … *生成の場*の要件を決める
   - 時間的性質（状態視点）: 不変 / 状態機械 / 陳腐化 … *保管の場*の要件を決める
   残課題 = 「一方向生成 × 状態機械」。だから「生成はどこでもいいが、保管は状態を持てる場所が要る」と一言で説明できる。

5. **「更新頻度」は時間的性質の"症状"に過ぎなかった。** 原因（時間的性質）で切るほうがクリア。

## 結晶した概念（再利用可能な道具）

### A. 情報を捉える 2 軸

| 軸 | 何を決めるか | 取りうる値 |
|---|---|---|
| 生成様式（イベント視点） | *生成の場*の要件 | 一方向 / 対話的 |
| 時間的性質（状態視点） | *保管の場*の要件 | 不変 / 状態機械 / 陳腐化 |

### B. 時間的性質の 3 分類（保管媒体を決める主軸）

| 時間的性質 | 意味 | 例 | 保管の含意 |
|---|---|---|---|
| 不変 | 生まれたら二度と変わらない | 判断ログ / Goal / Scope / verdict | ファイルに落として永久保存 |
| 状態機械 | open→closed の遷移を持つ | 残課題 / 指摘 / ステータス / PR | 現在状態を **1 箇所** で保つ必要。状態を持てる媒体 |
| 陳腐化 | 更新イベントは無いが外界で古くなる | 現状コンテキスト | 凍結して日付印 or 生成源へのリンク |

### C. コピー可否は時間的性質で決まる（drift の一般原理）

- **不変** → コピーしても drift しない（変わらないから）。要約・索引に自由に複製してよい。
- **状態機械** → コピーすると必ず drift する（現在値が複数箇所に分裂）。一次を 1 つに固定し、他は**リンクのみ**。
- **陳腐化** → 放置すると嘘になる。凍結印 or リンク置換。

> これが「要約重複が OK な場合と NG な場合」を機械的に判定する規準になる。
> 例: README ダッシュボードの drift は、README が**状態機械な情報（ステータス・PR 番号）を複製**していたから。
> 不変な情報だけを複製していれば drift は原理的に起きなかった。

### D. その他の結晶

- **一次ソースはフェーズで移動する**: 計画中は PR が無いのでファイル/README が状態を持つしかないが、
  PR 作成後は GitHub が実体になり、ファイルの値は二次に転落する。drift は「移動に運用が追いつかず、
  移動前の媒体に古い値が取り残される」ことで起きる（例: Plan の「PR: TBD」）。
- **媒体選択は 4 次元**: 情報の性質 × 媒体の性質 × 作業モード（Claude 完結 / GitHub 連携）× ライフサイクル段階。
- **レビューは 2 層**: プロセス（指摘⇄対応⇄解決 = 対話的・状態機械 → GitHub 向き）と
  結論（verdict = 不変・記録 → ファイルで足りる）。`Review.md` は後者しか表現できず、前者（解決状態の追跡）を殺している。

## まだ未解決の論点（Step 2 以降へ送る）

- **状態機械な情報を、GitHub と Claude 完結のどちらに固定するか**（作業モード依存の設計判断）。
- **生成様式（一方向 / 対話的）が媒体選択にどう効くか** = *生成の場*の要件は、まだ十分展開していない。
- **「一次ソースの移動」を運用でどう扱うか**: 移動を明示的に認めて各フェーズの正の媒体を定義するか、
  それとも「常にファイルが正・GitHub はミラー」等に固定して移動を無くすか。
