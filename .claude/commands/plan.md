# Plan コマンド

`/plan` は、実装前に要件・リスク・作業順序を整理するためのコマンド。
出力は日本語で作成し、保存対象の作業では Plan ファイルを
`outputs/plans/` に出力する。

## このコマンドで行うこと

1. **要件の再整理**: 何を作るか、何を作らないかを明確にする
2. **影響範囲の確認**: 変更対象のファイル、機能、設計を洗い出す
3. **リスク整理**: 技術的リスク、運用リスク、未確定事項を明示する
4. **実装手順の作成**: 段階的に確認できる作業順序へ分解する
5. **ユーザー確認待ち**: 実装へ進む前に、必ずユーザーの承認を待つ

## 出力先

保存対象の Plan は、次の場所に日本語で出力する。

```text
outputs/plans/YYYY-MM-DD-HHMM-<slug>.md
```

- `YYYY-MM-DD-HHMM` は Plan 作成時刻を JST で付ける
- `<slug>` は branch 名の末尾、または作業内容を kebab-case にした短い名前にする
- フォーマットは `outputs/plans/_template.md` を基準にする
- Review が作成されたら、Plan の `レビュー` 欄または本文からリンクする
- PR が作成されたら、Plan の `関連 PR` 欄を更新する

## 保存対象

以下のいずれかに当てはまる場合は、チャットだけでなく Plan ファイルを作成する。

- 複数ファイルまたは複数 package にまたがる作業
- DB / API / 認証 / 権限 / CI / デプロイに影響する作業
- PR 作成を前提にした作業
- ユーザーが Plan Mode、計画、設計、事前承認を求めている作業
- 判断理由やリスクを後から参照したい作業

typo 修正や 1 ファイル内の小さな調整は、ユーザーが明示しない限り
チャット内の Plan で完結してよい。

## 使うタイミング

`/plan` は以下の場面で使う。

- 新機能を始めるとき
- 設計変更やアーキテクチャ変更を行うとき
- 複雑なリファクタリングを行うとき
- 影響範囲が複数ファイルに広がるとき
- 要件が曖昧で、実装前に確認したいとき

## 出力フォーマット

Plan ファイルは、原則として以下の見出しを含める。

```markdown
# Plan: <作業名>

| 項目 | 値 |
|---|---|
| 作成日時 | YYYY-MM-DD HH:MM JST |
| 担当 | Claude Code + <担当者> |
| ブランチ | `<branch-name or TBD>` |
| 関連 PR | TBD |
| レビュー | TBD |

## 目的

## スコープ

## 現状コンテキスト

## 実装計画

## 検証

## リスク

## 判断ログ

## ステータス
```

## 重要ルール

- Plan は日本語で書く
- 実装前にユーザーの明示的な承認を待つ
- 承認前にコード変更を開始しない
- 方針変更が発生した場合は、Plan を無言で上書きせず `判断ログ` に残す
- Review は同じ `<slug>` を使い、対象 Plan へのリンクで対応付ける（HHMM はズレてよい）

ユーザーが修正を求めた場合は、次のように扱う。

- `修正: ...` → Plan を更新し、必要なら `判断ログ` に残す
- `別案: ...` → 代替案として再整理する
- `この範囲だけ先に` → `スコープ` と `実装計画` を縮小する

## 関連コマンド

- `/code-review`: 実装後または PR 前のレビューを日本語で作成する
- `/tdd`: テスト駆動で実装を進める
- `/verify`: 実装後の検証を行う
