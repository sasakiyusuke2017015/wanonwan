# Step 1b: 情報軸の評価（＋生データ）

> 各**情報項目**を、[thinking-log の道具](../../../docs/thinking-log/2026-07-06-information-properties-and-placement.md)
> = 〈生成様式（一方向 / 対話的）× 時間的性質（不変 / 状態機械 / 陳腐化）〉で分類し、
> そこから**推奨一次媒体**と**コピー可否**を導く。ドキュメント軸は [01a](01a-by-document.md)。
>
> 分析の骨（thinking-log C より）: **不変=コピー可 / 状態機械=一次1つ+リンク / 陳腐化=凍結印**。

## §1 情報項目カタログ（性質 → 推奨媒体）

| 情報項目 | 生成様式 | 時間的性質 | 推奨一次媒体 | コピー可否 |
|---|---|---|---|---|
| 意思決定の理由（判断ログ） | 対話的 | 不変 | ① Plan | 複製可（要約 OK） |
| Goal / Scope | 対話的 | 不変 | ① Plan | 複製可 |
| リスク | 対話的 | 不変（記録） | ① Plan | 複製可 |
| 実装計画 | 一方向 | 不変（記録） | ① Plan | 複製可 |
| 現状コンテキスト | 一方向 | **陳腐化** | ① Plan（注意） | 凍結印 or リンク |
| **フェーズ状態** | 一方向 | **状態機械** | ⑥ GitHub（PR 後）/ ③ README（計画中） | **一次1つ+リンク** |
| **PR 番号 / ブランチ** | 一方向 | 状態機械 | ⑥ GitHub | **リンクのみ** |
| レビュー **verdict** | 対話的 | 不変 | ② Review | 複製可 |
| レビュー **個別指摘の解決状態** | 対話的 | **状態機械** | ⑥ GitHub PR review | **一次1つ** |
| **残課題 / TODO** | 一方向 | **状態機械** | ⑥ GitHub Issue 候補 / ① Plan | **一次1つ** |
| 検証チェック（マージ後） | 一方向 | 状態機械 | ① Plan（現状） | 一次1つ |
| CI 結果 | 一方向（自動） | 状態機械→確定後不変 | ⑥ GitHub Actions | リンク |
| コード実体 | — | 状態機械 | コード / ⑥ | — |

**読み取り**: 「状態機械」の行（フェーズ状態・PR 番号・指摘解決・残課題・検証チェック・CI）が、
**複製すると必ず drift する危険帯**。現状はこれらの多くを ① Plan / ③ README に手書きコピーしている。

## §2 現状の所在マトリクス（どこに実在するか）

●=記述あり / ◎=本来の一次ソース。根拠は §3 の生データ。

| 情報項目 | ① Plan | ② Review | ③ README | ④ GitHub | 判定 |
|---|:--:|:--:|:--:|:--:|---|
| 判断ログ | ◎ | | | | ✅ 一元（不変・複製なし） |
| Goal / Scope / リスク | ◎ | | | | ✅ 一元 |
| 実装計画 | ◎ | | | | ✅ 一元 |
| 現状コンテキスト | ●(陳腐化) | | | ◎(コード) | 🟡 凍結印が無い |
| **フェーズ状態** | ●●(ヘッダ+末尾) | | ● | (PR状態) | 🔴 状態機械を3層コピー＝drift |
| **PR 番号 / ブランチ** | ●(手書き) | ●(メタ) | ●(手書き) | ◎ | 🟠 状態機械を手書き＝drift 発生済 |
| レビュー verdict | ●●(2箇所) | ◎ | ● | ●(PR) | 🟠 不変だが4箇所は過剰（実害は小） |
| 指摘の解決状態 | ●(残課題に列挙) | ●(Findings) | | (PR review) | 🔴 状態機械なのにファイルが状態を持てない |
| 検証チェック | ◎ | | | | ✅ ここだけの固有・一次 |

> 不変な情報（判断ログ等）は複製しても平気なので✅。
> **問題は例外なく「状態機械 × 複製」の交差点**（🔴🟠）に集中している。thinking-log C の予言通り。

## §3 生データ（根拠）— urgency-list-display の実棚卸し

分析の確からしさを追えるよう、代表 1 件の**実際の記述**を棚卸しする。

### 3-1. ① Plan `urgency-list-display.md`（主要箇所）

| 箇所 | 情報 | 生成×時間 | 備考 |
|---|---|---|---|
| ヘッダ「ステータス」 | `🟣 コードレビュー APPROVE…` | 状態機械 | 末尾チェックリスト・README と重複。表示名に verdict 混在 |
| ヘッダ「関連 PR」 | `TBD` | 状態機械 | **GitHub は #79。未反映（drift）** |
| ヘッダ「レビュー」 | Review リンク+APPROVE | 不変 | Review verdict のコピー |
| ヘッダ「担当/git repo/slug」 | 固定値 | — | 定型ノイズ（全 Plan 同一） |
| 目的 / スコープ | ゴール・境界 | 不変 | ✅ 一次 |
| 現状コンテキスト | 実装前の既存実装 | 陳腐化 | 実装後に古くなる |
| 判断ログ | 決定と理由 6 行 | 不変 | ✅ 最重要・一次 |
| 未確定事項 | 問い+「決着」追記 | 一部不変 | 決着分が判断ログと二重 |
| 残課題 | NICE-TO-HAVE 3 件 | 状態機械 | Review Findings の要約 |
| ステータス（末尾） | フェーズ+検証チェック | 状態機械 | フェーズ部はヘッダと重複／検証チェックは固有 |

### 3-2. ② Review `…-review.md`

| 箇所 | 情報 | 生成×時間 |
|---|---|---|
| 項目表「verdict」 | `APPROVE` | 不変（一次） |
| 判定スコープ表 | 最終/Plan/実装/記録整理 | 不変（Review 固有） |
| Findings | NICE-TO-HAVE ×2 | 状態機械（解決状態を持てない） |

### 3-3. ③ README（urgency-list-display 行）

| 列 | 実際の値 | 時間的性質 | 備考 |
|---|---|---|---|
| ステータス | `🟡 計画中（未着手）` | 状態機械 | **Plan 本体は🟣。drift** |
| 関連 PR / レビュー | `TBD` | 状態機械 | **実体 #79。drift** |
| 推奨アクション | `未確定事項を確定→実装着手` | 状態機械 | 実態は実装完了。drift |

## §4 drift の実測（1 件で3層すべて食い違う）

| 情報 | ① Plan 本体 | ③ README | ④ GitHub |
|---|---|---|---|
| フェーズ状態 | 🟣 承認待ち | 🟡 計画中 | PR #79 open |
| PR 番号 | TBD | TBD | #79 |

3つとも不一致。原因は「状態機械（フェーズ・PR）を3箇所に手書きコピーし、更新が追いつかない」こと。
これは thinking-log D「一次ソースはフェーズで移動する／移動前の媒体に古い値が残る」の実例。

## この Step の確認事項（情報軸）

1. §1 カタログの「生成様式 × 時間的性質」の割り当てに違和感がないか
2. **「問題は例外なく〈状態機械 × 複製〉の交差点に集中する」**という結論が、生データ（§3/§4）から腹落ちするか
3. これで Step 1（現状整理）を**合意済みの事実**として確定してよいか → 次は Step 2（あるべき姿の原則）
