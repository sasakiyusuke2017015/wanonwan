# Step 1a: ドキュメント軸の評価

> 各ドキュメントを「目的 / 持つ情報 / 情報の性質（更新頻度）/ そこにあるべき理由 / 他との関係 / 現状の問題」で評価する。
> [01-current.md](01-current.md) の登場人物 ①〜⑦ に対応。情報軸の分析は [01b-by-information.md](01b-by-information.md)。

一覧サマリ（詳細は各節）:

| # | ドキュメント | 一番の目的 | 主な更新頻度 | 現状のいちばんの問題 |
|---|---|---|---|---|
| ① | Plan 本体 | 意思決定と計画の記録 | 計画時に集中、以後まばら | 揮発情報を抱え込み drift 源になっている |
| ② | Review | レビュー判定の記録 | 1 レビュー = 1 回、以後不変 | verdict が Plan・README にコピーされ散る |
| ③ | README | 全 Plan 進捗の索引 | Plan 状態が変わるたび | Plan 更新に追随できず陳腐化 |
| ④ | テンプレ | Plan のひな型 | ほぼ不変 | 実運用と乖離・Review 版が欠落 |
| ⑤ | 運用ルール | 書き方・遷移の規定 | まれ | 参照先（テンプレ）と実態がズレ |
| ⑥ | GitHub | 実装・進捗の実体 | 常時 | 実体なのに Plan/README へ手書き転記されている |
| ⑦ | CLAUDE.md | rules への入口 | まれ | （本題では大きな問題なし） |

---

## ① Plan 本体

- **目的**: 「この作業で何を、なぜそう作るか」を計画し、後から辿れる意思決定の記録として残す。
- **持つ情報**: ヘッダ表（ステータス/slug/日付/担当/ブランチ/関連 PR/レビュー/前提 Plan/git repo）、
  目的、スコープ、現状コンテキスト、実装計画、検証、リスク、（実運用で追加された）未確定事項・判断ログ・残課題、
  末尾ステータス（チェックリスト）。
- **情報の性質（更新頻度）**: 大半は**不変層**（計画・判断ログ・Goal/Scope は実装完了でほぼ凍結）。
  だが実際にはヘッダの「ステータス/関連 PR/レビュー」と末尾チェックリストという**揮発層**を抱えている。
  つまり 1 ファイルの中に「凍結してよい情報」と「頻繁に変わる情報」が混在している。
- **そこにあるべき理由**: 意思決定の理由・判断ログは**ここにしか残らない**（git log は差分、PR は結論のみで理由が薄い）。
  時間が経つほど価値が上がる、この体系で最も代替不能な情報。
- **そこにあるべきでない情報**: 揮発層（フェーズ状態・PR 番号・verdict）。実体は GitHub / README にあり、手書きは drift を生む。
- **他との関係**: ④テンプレを雛形に生成 → ②Review と slug でペア → ③README に要約される → ⑥GitHub PR と相互リンク。
- **現状の問題**: (a) 揮発層を抱えて drift 源になる、(b) ヘッダと末尾でフェーズ状態が二重、
  (c) 未確定事項の決着が判断ログと二重、(d) 現状コンテキストが実装後に陳腐化。

## ② Review

- **目的**: 1 作業のレビュー結果（合否と指摘）を判定として固定する。
- **持つ情報**: 項目表（対象 Plan/slug/種別/レビュアー/日付/対象コミット/verdict）、サマリ、
  判定スコープ表（最終/Plan/実装/記録整理）、Findings、Verdict。
- **情報の性質（更新頻度）**: **1 レビュー = 1 回書いたら不変**。再レビューは新セクション追記 or 別ファイル。
  性質としては「ある時点の判定のスナップショット」で、後から書き換えない前提。
- **そこにあるべき理由**: verdict と Findings の**一次ソース**。「なぜ APPROVE か / 何が指摘されたか」の出どころ。
- **そこにあるべきでない情報**: Plan の内容の再掲（サマリが Plan と重複しがち）。
- **他との関係**: ①Plan と slug ペア。verdict は③README に要約リンクされる。Findings は①Plan「残課題」に要約される。
- **現状の問題**: (a) verdict が Review・Plan ヘッダ・Plan 末尾・README の 4 箇所に散る、
  (b) `reviews/_template.md` が無く様式が個々のレビューに委ねられている。

## ③ README ダッシュボード

- **目的**: 全 Plan の進捗を 1 画面で俯瞰する索引。「次に何をすべきか」を一覧する。
- **持つ情報**: Plan ごとに（リンク / ステータス / 関連 PR・レビュー / 推奨アクション）。表頭に「一次ソースは Plan 本体」の注記。
- **情報の性質（更新頻度）**: **純粋な揮発層**。Plan の状態が変わるたびに追随更新が必要。中身は全て他所（Plan/Review/GitHub）の二次コピー。
- **そこにあるべき理由**: 一覧性。個々の Plan を開かずに全体像を掴む価値は本物で、GitHub の PR 一覧では「Plan 単位の進捗」は見えない。
- **そこにあるべきでない情報**: 独自の一次情報は持たない（持つと Plan と競合する）。あくまで要約。
- **他との関係**: ①Plan と②Review の要約先。⑤rules が「Plan 状態変更時は同 PR で README も更新」と規定。
- **現状の問題**: **追随更新が構造的に漏れる**。urgency-list-display 行は「🟡 計画中・PR TBD」のまま実体は「PR #79・承認待ち」。
  「要約は手動同期」というモデル自体が drift を必然にしている。

## ④ Plan テンプレ `_template.md`

- **目的**: Plan の様式を固定し、必要セクションの抜けを防ぐ。
- **持つ情報**: ヘッダ表の項目定義 + 本文節の枠（目的/スコープ/現状コンテキスト/実装計画/検証/リスク/判断ログ/ステータス）。
- **情報の性質（更新頻度）**: ほぼ**不変**。様式変更時のみ。
- **そこにあるべき理由**: 「Plan に何を書くべきか」の唯一の規範。ここを直せば以後の Plan に効く（＝本作業の主要な出力先）。
- **現状の問題**: (a) 実 Plan にある「未確定事項 / 残課題 / 更新日」が**テンプレに無い**（実運用がテンプレを追い越している）、
  (b) ヘッダに定型ノイズ（担当 / git repo / slug）を最初から埋め込んでいる、
  (c) 対になる `reviews/_template.md` が存在しないのに rules は参照している。

## ⑤ 運用ルール `plan-review-workflow.md`（＋関連 rules）

- **目的**: Plan/Review/README/テンプレの書き方・保存先・状態遷移・ダッシュボード運用を規定する。
- **持つ情報**: 役割分担、保存パス規約、Plan/Review の必須項目、ステータス凡例（🟣 等）、
  「状態変更時は README も同 PR で」等の更新ルール、verdict とダッシュボード表示名の対応。
- **情報の性質（更新頻度）**: まれに更新。**規範層**。
- **そこにあるべき理由**: 体系全体の一次ソース（=「どう運用するか」の正）。
- **現状の問題**: (a) 存在しない `reviews/_template.md` を参照、
  (b) 「表示名に verdict を混ぜない」等の規定が実 Plan で守られていない（規則はあるが強制力＝チェックが無い）。
  規則自体の欠陥というより「規則⇔実態のズレを検知する仕組みが無い」。

## ⑥ GitHub（PR / Actions / branch）

- **目的**: 実装差分・レビュー・CI・マージという**実際の作業の実体**を持つ。
- **持つ情報**: PR 番号・状態（open/merged）、ブランチ、CI 結果、コードレビューコメント、マージ承認。
- **情報の性質（更新頻度）**: **常時変化する揮発層の実体**。ここが動くのが「真実」。
- **そこにあるべき理由**: PR 番号・マージ状態・CI は GitHub が定義上の一次ソース。Plan/README はそれを指すべき。
- **他との関係**: ①Plan と相互リンク。②Review は GitHub のコードレビューを Plan 体系に持ち込んだもの。
- **現状の問題**: 実体なのに、PR 番号・状態が Plan ヘッダと README に**手書き転記**されている（転記漏れ＝drift）。

## ⑦ CLAUDE.md

- **目的**: 毎セッション投入され、rules へ誘導する入口。
- **情報の性質**: まれに更新。本題（Plan 二重管理）では大きな問題は無い。
- **関係**: ⑤rules へのリンク元。本作業の結論を rules に反映すれば、CLAUDE.md 側の変更は基本不要。

## この Step の確認事項（ドキュメント軸）

1. 各ドキュメントの**「目的」と「あるべき/あるべきでない情報」**の言語化に違和感はないか
2. 「更新頻度（不変 / 揮発 / スナップ）」の判定が実感と合っているか
3. ③README を「純粋な揮発層・二次コピーのみ」と位置づけた点に同意できるか
   （＝README は独自情報を持たず、drift の是正は『同期の自動化 or 縮小』方向、という含意）
