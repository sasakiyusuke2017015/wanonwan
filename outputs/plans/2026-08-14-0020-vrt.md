## 目的

Storybook 資産はあるが VRT は未配線。**ダークモード（Phase 3）が 143 箇所のハードコード色を
semantic トークンへ置換する前に、light の見た目が不変であることを機械的に検出できる状態**を作る。

安全網の本質は「ダークを守る」ことではなく「**トークン化・置換しても light が変わらない**」の担保。
そのため light baseline を先に確立し（4-light）、Phase 3 を additive に実装し、
ダーク撮影は後から**新規 image キーとして加算**する（4-dark）。

## スコープ

### やること

- 撮影層の選定と配線（storycap の Storybook 10.5 互換 spike → NG なら Playwright 薄スクリプト）
- flaky 対策（アニメーション無効化・日付固定・font 読み込み待ち）を撮影層に同梱
- **catalog 171 stories** の light 撮影
- **app ページの light 撮影**（Playwright 新規導入）— 143 箇所は app 側にあり story が 0 のため、
  catalog 撮影だけでは Phase 3 の安全網にならない
- reg-suit 設定（`reg-keygen-git-hash` + `reg-notify-github` + `reg-publish-s3-plugin`）
- CI workflow（storybook build → 撮影 → compare → 差分レポート）
- 残置 chromatic（依存 + `storybook:deploy`）の整理

### やらないこと（スコープ外）

- **ダーク撮影（4-dark）**。Phase 3 完了後に新規 image キーとして加算する別作業
- Chromatic の採用（SaaS 非採用方針。残置は整理対象）
- E2E テストとしての Playwright 活用（本 Plan の Playwright は**スクリーンショット取得専用**）
- `test:storybook`（`@storybook/addon-vitest`）の配線。VRT とは別軸のため触らない
- a11y 自動チェックの CI 配線（addon-a11y は導入済みだが本 Plan の対象外）

## 実装計画

**A → B → C は stg 非依存で進められる。D 以降が stg MinIO 待ち。**

1. **A. 撮影層の spike**（`experiment/vrt-capture`）
   storycap が Storybook **10.5.2** で動くかを実際に確認する。動かなければ
   `storybook-static/index.json` + `iframe.html?id=` を Playwright で回す薄いスクリプトへフォールバック。
   どちらを採るかを判断ログに記録する。
2. **B. flaky 対策 + ローカル baseline**（`feature/vrt-capture`）
   アニメーション無効化（`prefers-reduced-motion` + CSS 強制）・日付固定・font 読み込み待ちを
   撮影層に同梱。ローカルで 2 回撮って**差分ゼロ**になることを確認する。
3. **C. app ページ撮影**（`feature/vrt-app-pages`）
   Playwright を devDependency として新規導入。dev スタック起動 + `provision:dev` 済みの DB に対し、
   143 箇所を含む画面を列挙して撮影する。ログイン状態は `admin1` / `member1` 等の固定アカウントで作る。
   撮影対象ページの一覧は本 Plan の「撮影対象」節を一次とする。
4. **D. reg-suit 設定 + baseline 保管**（**stg MinIO 待ち・ブロック**）
   `reg-publish-s3-plugin` の `customEndpoint` で MinIO を指す。`reg-keygen-git-hash` で
   baseline commit を解決し、`reg-notify-github` で PR にレポートを出す。
5. **E. CI workflow**（**D に依存**）
   storybook build → 撮影 → compare → レポート。
6. **F. chromatic 残置の整理**（`refactor/drop-chromatic`）
   依存と `storybook:deploy` script を削除する（stg 非依存・独立して出せる）。

### 撮影対象（app ページ・C の一次リスト）

143 箇所を含む 33 ファイルが載る画面を網羅する。ログイン別に分ける。

| ロール | 画面 |
|---|---|
| 未ログイン | `/login` / `/change-password` |
| member | `/`（ダッシュボード）/ `/surveys` / `/surveys/[publishId]` / `/schedule` |
| interviewer | 担当面談一覧 / 面談記録 |
| admin | `/admin/users` / `/admin/surveys` / `/admin/answers` / `/admin/questions` / `/admin/org` / `/admin/positions` / `/admin/urgencies` + 各 new / edit |

## 検証

- **A**: storycap（または代替）が 171 stories を撮り切り、PNG が出力される
- **B**: 同一 commit で 2 回撮影 → reg-suit compare で**差分 0 件**（flaky でない）
- **C**: app 撮影が 143 箇所を含む全画面をカバーする（撮影漏れをファイル単位で突合）
- **D/E**: 意図的に 1 色だけ変えた commit で**差分が検出され PR にレポートが出る** /
  baseline 承認フロー（承認 → 次回から差分なし）が回る
- **F**: `pnpm --filter @ui-catalog/core exec storybook build` が chromatic 削除後も通る
- 共通: `pnpm turbo run typecheck lint build test`

## リスク

| リスク | 対応 |
|---|---|
| **storycap が Storybook 10.5 に非対応**（reg-suit 定番だが追従が遅れがち） | A を spike として独立させ、NG なら `index.json` + Playwright の薄いスクリプトへフォールバック。どちらでも B 以降の設計は変わらない |
| **baseline の CI 到達性が stg CD 再開に依存**し、Phase 3 の安全網が間に合わない | D/E をブロック項目として明示し、A〜C・F を先行させる。stg が長引く場合は「ローカル baseline + 手動 compare」で Phase 3 を回す暫定運用に切り替える（判断ログに追記して判断） |
| **Playwright 導入でスコープが膨らむ**（ブラウザバイナリ・CI 時間・DB 前提） | 用途をスクリーンショット取得だけに限定し、E2E アサーションは書かない。CI では chromium 1 種のみ |
| app 撮影が **DB 状態に依存**して flaky | `provision:dev` の固定 seed（36 アカウント + demo）を前提にし、撮影前に必ず fresh init する。日付表示は撮影層の日付固定で吸収 |
| VRT flaky（アニメ・live date・font）で偽陽性 diff | B で「2 回撮って差分 0」をゲートにする。通らなければ原因を潰すまで先へ進めない |
| 171 stories + app 数十画面で **CI 時間が伸びる** | 撮影を並列化し、PR では変更のあった領域のみ撮る運用を検討（E で計測してから判断） |
| ダーク撮影追加時に**全 story の差分が爆発** | 4-dark は既存 baseline の上書きではなく**新規 image キーの加算**にする（別作業だが設計として明記） |
