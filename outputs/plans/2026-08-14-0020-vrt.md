## 目的

Storybook 資産はあるが VRT は未配線。**ダークモード（Phase 3）が 143 箇所のハードコード色を
semantic トークンへ置換する前に、light の見た目が不変であることを機械的に検出できる状態**を作る。

安全網の本質は「ダークを守る」ことではなく「**トークン化・置換しても light が変わらない**」の担保。
そのため light baseline を先に確立し（4-light）、Phase 3 を additive に実装し、
ダーク撮影は後から**新規 image キーとして加算**する（4-dark）。

## 実装計画

1. **A. 撮影層の spike**（`experiment/vrt-capture`）
   storycap が Storybook **10.5.2** で動くかを実際に確認する。動かなければ
   `storybook-static/index.json` + `iframe.html?id=` を Playwright で回す薄いスクリプトへフォールバック。
   どちらを採るかを判断ログに記録する。
2. **B. flaky 対策 + ローカル baseline**（`feature/vrt-capture`）
   アニメーション無効化（`prefers-reduced-motion` + CSS 強制）・日付固定・font 読み込み待ちを
   撮影層に同梱。ローカルで 2 回撮って**差分ゼロ**になることを確認する。
3. **C. app ページ撮影**（`feature/vrt-app-pages`）
   Playwright を devDependency として新規導入。dev スタック起動 + `provision:dev` 済みの DB に対し、
   143 箇所を含む画面を列挙して撮影する。ログイン状態は `admin1` / `member1` 等の固定アカウントで作る。
   撮影対象ページの一覧は本 Plan の「撮影対象」節を一次とする。
   **CI 再現性を設計時点で担保する**: CI は既に compose 起動 + `provision:dev` を実行しているため、
   撮影スクリプトはその状態を前提にできる形にし、ローカル専用の手順（手動ログイン等）を作らない。
4. **D1. reg-suit compare（ローカル baseline）**（`feature/vrt-compare`）
   reg-suit の compare は S3 を必要としない。baseline を作業ディレクトリに置いて
   `reg-suit run` で差分レポート（HTML）を出せる状態にする。**安全網としてはここで成立**し、
   Phase 3 の各 PR はこれを使って light 不変を確認できる。
5. **F. chromatic 残置の整理**（`refactor/drop-chromatic`）
   依存と `storybook:deploy` script を削除する（独立して出せる）。

## A/B の実測（2026-08-23・spike 結果）

### 撮影層

storycap は Storybook 10.5 に非対応のため不採用。`storybook-static` を静的配信し、
`index.json` の story 一覧を `iframe.html?id=<id>` で 1 件ずつ開いて Playwright で撮る。
日本語 story id（`アニメーション-animated--fade` 等）も URL エンコードで問題なく扱える。

mount 完了判定は **`#storybook-root` に子要素があり、かつ `body.sb-show-main` が付く**こと。
`.sb-loader` / `.sb-previewBlock` はマウント後も hidden で DOM に残るため、存在判定に使わない。

### アニメーションは 3 系統あり、対策がそれぞれ異なる

| 系統 | 例 | `document.getAnimations()` | CSS 無効化 / `reducedMotion` | 対策 |
|---|---|---|---|---|
| CSS animation / transition | `animate-spin`（Spinner）・shimmer・`SpaceBackground` | 現れる | 効く | `animation-play-state: paused` + **負の `animation-delay`** |
| **JS スプリング**（framer-motion） | `NumberTicker`（`useSpring`）・`BlurFade`（`motion` + `useInView`） | **現れない** | **効かない** | `isCaptureMode()` で最終状態へ確定（`spring.jump()` / `duration: 0`） |
| **SMIL**（SVG 内の `<animate>` / `<animateTransform>` `repeatCount="indefinite"`） | `Icon` の `loading-*`（`loading-dna` 等） | **現れない** | **効かない** | `svg.pauseAnimations()` + `setCurrentTime(0)` |
| **JS ライブラリのアニメーション** | recharts（`PieChart` / `TrendChart` の `isAnimationActive`）・`TrendChart` のパーティクル rAF | **現れない** | **効かない** | `isCaptureMode()` で `isAnimationActive={false}` / rAF ループを開始しない |
| **描画内容そのものが非決定** | `LoadingZone` のスケルトン幅・`InteractiveTable` の story フィクスチャ（`Math.random()`） | — | — | 撮影層で `Math.random` を **seed 付き mulberry32 に差し替え** |
| **現在時刻の表示** | `RefreshButton` の「最終更新 HH:mm」（`new Date().toLocaleTimeString`） | — | — | 撮影層で `context.clock.install()` + `pauseAt()` により時刻を固定 |

下 4 系統は CSS からも WAAPI からも触れないため、**capture 層の CSS だけでは静止できない**。
これが `packages/ui` に capture-mode を入れた理由。

**負の `animation-delay` は `-600s`** とする。`-1ms` では、`SpaceBackground` の
`starDrift`（180/320/520s）や `nebulaPulse`（14s・delay 9s）のような長尺アニメが
並列撮影時の mount タイミング差でわずかに進み、非決定が残った。
最長の周期より大きい負値を与え「1 周し終えた位置」で確実に止める。

### capture-mode の入口（既定オフ・本番挙動は不変）

- `window.__VRT_CAPTURE__ = true` … `isCaptureMode()`（`core/utils/captureMode.ts`）が読む。JS アニメを最終値へ確定
- `<html data-vrt-capture="true">` … `globals.css` の撮影モード block を有効化。CSS アニメを先頭フレームで停止

いずれも撮影層が `addInitScript` で注入する。**フラグ未設定なら完全に無効**で、
未設定時に `NumberTicker` が `¥0 → ¥1249999` とカウントアップし SMIL も動作することを実測確認済み。

SMIL は後からマウントされる `<svg>` にも効かせる必要があるため、撮影層は `MutationObserver` で
追加ノードを監視し、`svg` を見つけ次第 `pauseAnimations()` + `setCurrentTime(0)` する。

### 安定性の実測

| 条件 | 結果 |
|---|---|
| 無対策 | 24 件中 **6 件が不安定**（25%） |
| CSS 無効化 + `reducedMotion` | 24 件中 **7 件**（改善せず） |
| capture-mode 全部入り（狙い撃ちサンプル 12 件） | **11/12 安定**（残 1 = SMIL） |
| capture-mode + SMIL 凍結（同 5 件） | **5/5 安定** |
| カタログ横断サンプル 35 件 × 2 回 | 35/35 安定 |
| 全 962 stories × 2 回（1 回目） | 942/962（不安定 20 = BlurFade / recharts / LoadingZone 系） |
| **全 962 stories × 2 回（対策後）** | **962/962 安定**・707 秒・**734ms/枚**（concurrency 4） |

> 撮影速度は測定機（Windows・他プロセス稼働中）での参考値。負荷時に mount timeout が散発したため、
> **CI 時間の見積りは E で静かなランナー上で測り直す**こと。

## D1 の実測（2026-08-23）

compare エンジンは **reg-cli 0.18.9**（reg-suit が内部で使うもの）。S3 を必要とせず、
`expected` / `actual` の 2 ディレクトリを渡すだけで差分 HTML レポートが出る。

```bash
pnpm --filter @ui-catalog/core storybook:build
pnpm --filter @ui-catalog/core vrt:baseline   # .vrt/expected を作る（変更前に 1 回）
# ここでコードを変更する
pnpm --filter @ui-catalog/core storybook:build
pnpm --filter @ui-catalog/core vrt:capture    # .vrt/actual
pnpm --filter @ui-catalog/core vrt:compare    # 差分があれば exit 1 + report.html
```

`vrt:compare` は差分検出時に **exit 1** を返すので、そのまま CI ゲートに使える。
`vrt:flaky` は同じ story を 2 回撮って差分の有無だけを見る（撮影層自体の健全性チェック）。

| 検証 | 結果 |
|---|---|
| 無変更で 2 回撮って compare | **79/79 pass・changed 0** |
| `Button.module.scss` の `.danger` グラデーションを緑に変えて compare | **13 stories を changed として検出** |
| 差分レポート | `report.html`（352KB）+ `diff/*.png`（変更領域が赤くハイライト） |

検出された 13 件には `button--danger` 本体だけでなく、**`ResetButton` / `KeyButton` /
`AsyncActionButton` など派生コンポーネント**も含まれた。手動レビューでは追い切れない

### app ページ撮影で判明した落とし穴

| 事象 | 原因と対処 |
|---|---|
| ログインが 30 秒 timeout | ログイン画面は入力欄をレスポンシブで 2 組描画する。セレクタ全体に `fill` すると片方が空のまま送信される → `.first()` で 1 組に絞る |
| 一覧が 0 件で詳細に辿れない | `clock.pauseAt()` が `setTimeout` ごと凍らせ、TanStack Query のデータ取得も `router.replace` も進まなくなっていた → **app では `install` だけ行い時計は止めない**（story は静的なので止めてよい） |
| `tbody tr` が見つからない | 一覧は取得完了後に描画される。即 `count()` せず `waitFor({state:'visible'})` で待つ |
| 詳細への遷移方法が画面ごとに違う | `<a href>` ではなく `onClick` + `router.push` の画面がある（SurveyCard の「回答する」ボタン・DataTable の `onRowClick`）。セレクタは対象ごとに指定し、遷移判定は URL 変化で見る |
