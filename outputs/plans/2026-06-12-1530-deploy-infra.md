## 1. ゴール / 非ゴール

### ゴール

waoon を **stg / prod で安全に起動・更新**できる基盤を作る。

- `apps/web` の **本番 Dockerfile** + **stg/prod の docker-compose**（dev と同型 + 本番差分）。
- **nginx**（TLS 終端・ルーティング・X-Forwarded-For 注入、必要ならエッジ rate-limit）。
- **secrets 管理**: dev フォールバック（`dev-only-change-me…`）が **prod で絶対に使われない**保証。
- **CD**: GitHub Actions で build → （registry）→ host 反映 → `db:migrate` → 起動 の一連を定義。
- **prod 初期化**: 組織マスタ seed のみ + **admin 1 名を GoTrue 経由で provisioning**（手書き UUID seed は使わない）。
- **DB バックアップ/リストア**方針。

### 非ゴール

| 項目 | 理由 |
|---|---|
| 実データ移行（Pleasanter→Postgres） | 親 Plan の非ゴールのまま。初期状態は「空 + admin 1 名」 |
| 初回ログイン後の force-change / メール recover の本実装 | SMTP 方針（§4）次第。導入するなら別タスク |
| Redis 等の外部レートリミットストア | まず nginx で足りる。多重インスタンス化したら検討 |
| 監視/メトリクス/ログ集約・オートスケール | MVP のデプロイ後に別途 |
| ステージング以外の複数環境（プレビュー環境等） | 後 |

## 2. スコープ境界

- **触る**: `infra/Dockerfile.web`（新規）/ `infra/docker-compose.stg.yml` / `infra/docker-compose.prod.yml` / `infra/nginx/`（新規）/ `infra/.env.stg.example` `.env.prod.example` / `.github/workflows/`（CD 追加）/ `scripts/provision.mjs`（新規）/ ルート `package.json` scripts（`compose:stg/prod` 等）。
- **触らない**: 業務コード（`apps/web` のアプリ実装）・スキーマ DDL（既存のまま流す）・dev の `infra/docker-compose.yml`（dev は現状維持）。
- **前提（所与）**: Docker Compose / GitHub Actions / GoTrue `supabase/auth:v2.189.0` / postgres:15 自前 image。デプロイ先は §3 の「要決定」を確定してから。

## 3. 要決定（計画レビューで詰めたい論点）

実装着手前に確定が要る。**推奨案**を併記するが、最終決定は笹木さん。

| # | 論点 | 選択肢 | 推奨（暫定） |
|---|---|---|---|
| D-1 | デプロイ先ホスト | 既存 stg server(SSH/Docker) / VPS / マネージド | 技術メモの **stg server（Linux + Docker）** 前提で進める |
| D-2 | CD 方式 | push 型（GHCR に image → host pull）/ pull 型（host で git pull + build） | **push 型（GHCR）**。host は compose pull + up のみで軽い |
| D-3 | TLS 証明書 | certbot(Let's Encrypt) / 持ち込み証明書 | **certbot**（自動更新）。ドメインがある前提 |
| D-4 | レートリミット責務 | nginx 一次に移譲 / API 層と多層 | **多層**（nginx `limit_req` を一次、API 層 limiter は残す）。nginx が XFF 注入、API は実 IP を読む |
| D-5 | GoTrue SMTP | 入れる（recover/force-change 可能に）/ 入れない（admin 再発行のみ） | **当面入れない**（admin がパスワード再発行→別経路で通知）。SMTP は後続。`MAILER_AUTOCONFIRM=true` は維持 |
| D-6 | DB バックアップ | host cron `pg_dump` / pg_cron / マネージド | **host cron で日次 `pg_dump`** → host 外ストレージ。まず最小 |

## 4. 現状コンテキスト（差分の起点）

- **dev compose**: postgres + gotrue のみ。**web service・nginx は無い**（dev は `pnpm dev` 直起動）。
- **secrets フォールバック**: compose は `${JWT_SECRET:-dev-only-change-me-please-32bytes-minimum}` 等、**全 secret に dev default**。`AUTH_ADMIN_PASSWORD` `PG_SUPERUSER_PASSWORD` も同様。→ prod で env を渡し忘れても黙って dev secret で起動する穴（**B-2**）。
- **GoTrue**: `GOTRUE_DISABLE_SIGNUP=true` / `MAILER_AUTOCONFIRM=true` / SMTP なし / `SITE_URL`・`API_EXTERNAL_URL` が localhost 既定。
- **seed**: `10_users.sql` が GoTrue UUID 手書き（dev で作った id）。**prod では対応 identity が無く使えない**（**B-6**）。`scripts/provision.mjs` は未存在。
- **provisioning 実装は既にある**: `POST /api/v1/users` が GoTrue admin API で identity 発行 + `gotrue_id` 紐付け + 初期 PW 生成（#19）。prod 初期 admin は **これと同じ経路をスクリプト化**すればよい。
- **CI**: `.github/workflows/` で typecheck/build/pgTAP（#10, ✅）。CD は未。

## 5. 実装ステップ（順序付き）

> B-2（secrets 遮断）と B-6（prod admin provisioning）を最優先（事故・ログイン不能直結）。

### Step 1 — secrets 遮断 + env テンプレート（B-2）⟦最優先⟧
1. `docker-compose.prod.yml` では secrets の **default フォールバックを外す**（`${JWT_SECRET:?JWT_SECRET required}` 形式）。未設定なら起動失敗。
2. `.env.stg.example` / `.env.prod.example` を用意（必須キー列挙、値は空 or プレースホルダ）。実 `.env.*` は **リポジトリに入れない**（.gitignore 確認）。
3. **`dev-only-change-me` が prod に出ていない**ことの起動時 or CI チェック（grep ガード）を 1 つ入れる。
- 【検証】env 未設定で `compose -f prod up` が **起動失敗**すること。

### Step 2 — web の本番 image + stg/prod compose（B-1, N-2）
1. `infra/Dockerfile.web`（Next.js standalone build, `pnpm --filter @waoon/web build` → runner）。
2. `docker-compose.stg.yml` / `docker-compose.prod.yml`（postgres + gotrue + **web** + **nginx**、stg/prod 同一構成、env で差分）。dev は web を載せない非対称を明記（N-2）。
3. ルート `package.json` に `compose:stg:*` / `compose:prod:*`（親 Plan 例の命名に合わせる）。
- 【検証】stg compose で web まで起動し、nginx 経由でトップが描画。

### Step 3 — nginx（B-3, D-3, D-4）
1. `infra/nginx/`（`server_name`、TLS 終端=certbot、web への upstream、`proxy_set_header X-Forwarded-For` で**信頼できる実 IP を注入**）。
2. `limit_req`（zone）を一次レートリミットに。API 層 limiter は多層防御として残す（判断ログ D-4）。
- 【検証】HTTPS で到達 / `/api/v1/auth/login` を叩いて nginx 経由でも 429 が出る / API が XFF の実 IP を見ている。

### Step 4 — GoTrue prod 設定（B-4, D-5）
1. `SITE_URL` / `API_EXTERNAL_URL` を prod ドメインへ。`DISABLE_SIGNUP=true` 維持。`MAILER_AUTOCONFIRM=true` 維持（SMTP 無し方針）。
2. SMTP を入れない判断を判断ログに固定（recover は admin 再発行のみ・force-change は後続）。
- 【検証】prod GoTrue でログイン/refresh が通る。

### Step 5 — CD パイプライン + migration 運用（B-1, B-5, D-2）
1. GitHub Actions: main/develop の所定トリガで `Dockerfile.web` を build → **GHCR push**。
2. host 側 deploy（compose pull → `db:migrate`（web 起動前）→ web up）。手動 step か Actions の SSH deploy かを D-2 で確定。
3. migration は **前進のみ**（down なし）。失敗時は **fix-forward（人手）**と明記。
- 【検証】CD で stg が更新される。migration が web 起動前に流れる。

### Step 6 — prod provisioning + バックアップ（B-6, D-6, N-1）
1. `scripts/provision.mjs`: 組織マスタ seed（手書きユーザー行は除外）+ **admin 1 名を GoTrue admin API で発行 → `users.gotrue_id` 紐付け → 初期 PW を一度だけ表示**（#19 のロジックを CLI 化）。
2. 日次 `pg_dump`（host cron）→ host 外ストレージ。リストア手順（新 DB へ restore → `db:migrate`）を 1 段落で残す。
- 【検証】まっさらな prod で provision 実行 → その admin でログイン成功。`pg_dump` → 別 DB へ restore が通る。

## 6. 検証（受け入れ基準）

- env 未設定で prod compose が起動失敗（secrets 遮断）。
- `dev-only-change-me` が prod の起動構成に出ない（grep ガード green）。
- nginx 経由 HTTPS でアプリ到達、ログイン→保護ルート到達。
- CD で stg が更新され、migration が web 起動前に流れる。
- prod を空から `provision.mjs` で初期化 → 発行された admin でログイン成功。
- `pg_dump` バックアップ → 別環境へ restore → 起動成功。

## 7. リスクと緩和

| リスク | 影響 | 緩和 |
|---|---|---|
| dev secret が prod に漏れ起動 | 認証バイパス級 | Step 1 のフォールバック撤去 + grep ガード（最優先） |
| prod に手書き UUID seed が流れ、ログイン不能ユーザーが入る | 運用不能 | Step 6 で seed と provisioning を分離・手書きユーザーは prod に流さない |
| migration 失敗で prod 不整合 | データ事故 | 前進のみ + fix-forward 明記 + Step 6 バックアップで復旧可能に |
| XFF 詐称でレートリミット回避 | ブルートフォース | nginx が信頼できる実 IP を注入し API が trust（D-4） |
| TLS 証明書の更新漏れ | 接続不能 | certbot 自動更新（D-3） |
