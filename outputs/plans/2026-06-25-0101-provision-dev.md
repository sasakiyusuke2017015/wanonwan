## 目的

`pnpm provision:stg` / `provision:prod` はあるが **`provision:dev` が無い**。`scripts/provision.mjs`
は stg/prod 専用設計（dev secret を die・network は `waoon-stg/prod`・env ファイル必須）のため
dev で動かない。dev でも同じ provisioning フロー（任意 email の admin を GoTrue 発行 + public.users
紐付け + 初期 PW 一度表示）を一発で実行できるよう **dev モードを追加**し、3 環境を揃える。

## スコープ

### やること
- `scripts/provision.mjs` に **dev モード**を追加（`--dev` フラグで切替）:
  - network=`waoon`、compose=`infra/docker-compose.yml`、env ファイル不要（既定値で動く）
  - JWT_SECRET は dev 既定値（compose の `dev-only-change-me-...`）を使用
  - **secret ガードを環境別に反転**:
    - stg/prod（既存）: `JWT_SECRET` が dev 値なら die（現状維持）
    - dev（新規）: `JWT_SECRET` が dev 値**でなければ** die（`seed-gotrue-dev.mjs` と同じ逆ガード。stg/prod 誤爆防止）
- `package.json` に `provision:dev` を追加
- 既存挙動（random PW・force-change なし・00_org seed・orphan cleanup）は dev でも同一
- `public.users.email` に加えて `code` の重複も GoTrue 発行前にチェックする

### やらないこと
- stg/prod の provision 挙動・ガードは**変更しない**（dev 分岐の追加のみ。回帰させない）
- `seed-gotrue-dev.mjs`（固定 4 ユーザ）は残す。provision:dev は**任意 email の ad-hoc admin 作成**用で役割が違う（→ 判断ログ）
- GoTrue 到達は既存と同じ「compose network 上の使い捨て curl コンテナ → `http://gotrue:9999`」を踏襲（dev は network=`waoon` で解決可。localhost 方式へは変えない）

## 現状コンテキスト
- [scripts/provision.mjs](../../scripts/provision.mjs): `--compose-file` / `--env-file` / `--email` / `--name` / `--code` / `--network`。
  - network 既定: `compose-file` に `prod` を含めば `waoon-prod`、それ以外 `waoon-stg`。
  - [provision.mjs:47-50](../../scripts/provision.mjs#L47-L50): `JWT_SECRET` 未設定 or dev 値で die。
  - `psql()` は `docker compose --env-file <envFile> -f <compose> exec -T postgres ...` を使う（envFile 必須）。
- dev compose（[infra/docker-compose.yml](../../infra/docker-compose.yml)）: 先頭 `name: waoon` → **network 名 `waoon`**。env ファイルなし（`${JWT_SECRET:-dev-only-change-me-...}` 等の既定で動く）。
- 既に [seed-gotrue-dev.mjs](../../scripts/seed-gotrue-dev.mjs) が dev 用の固定ユーザ作成を担う（localhost:9999 + 逆ガード）。

## 実装計画
1. provision.mjs に `const isDev = flag("dev") !== undefined`（`--dev` 検出。flag() は値なし対応に調整）を追加。
2. 環境別の既定値:
   - dev: composeFile=`infra/docker-compose.yml`、network=`waoon`（**`--dev` 指定時は無条件で `waoon` 強制**。
     filename ヒューリスティックに頼らない）、envFile は **secret 取得に使わない**（dev は env ファイル無し前提）、
     PG_SUPERUSER=`postgres`/PG_DATABASE=`waoon`、JWT_SECRET=`process.env.JWT_SECRET ?? dev 既定`。
   - stg/prod: 現状維持。
3. secret ガードを分岐（**B-1**: 逆ガードが検査する変数 = `mintServiceRoleToken` が署名に使う変数と
   **同一の単一 `const JWT_SECRET`** とする。二重管理にしない＝ガード通過 secret と GoTrue 検証 secret の不一致を防ぐ）:
   - dev: `JWT_SECRET.includes("dev-only-change-me")` でなければ die。
   - stg/prod: 既存（dev 値なら die）。
4. `psql()` を envFile 任意対応に（dev は `--env-file` を付けない）。
   - **B-2（network フォールバック安全化）**: `--dev` 無しで **dev compose（`infra/docker-compose.yml`）が
     指定されたら die**（「dev compose には `--dev` が必要」）。現状の「`prod` を含まなければ `waoon-stg`」という
     曖昧フォールバックが dev compose 指定時に `waoon-stg` へ刺さるのを防ぐ。stg/prod の既存判定（実 stg/prod
     compose 名 → waoon-stg/prod）はそのまま温存。
   - **N-2**: `--dev` + 非 dev compose（stg/prod compose）の矛盾指定は die（`--dev` は dev compose 以外を受けない）。
   - **N-1**: dev モードは `--env-file` を **secret 取得に使わない**（dev は `process.env.JWT_SECRET ?? dev 既定`）。
     env ファイルを併せて渡しても secret 判定は process.env を優先（混乱を避けるため dev は env ファイル無視を明示）。
5. `public.users` 既存チェックを `email` だけでなく `code` も見るようにする（**N-3**: email チェックと
   code チェックを **GoTrue 発行前に独立した 2 つの die** として走らせる。どちらかが既存なら発行しない）。
   - 現行既定 `code=admin` は dev seed の `admin@example.com` と衝突するため、ad-hoc admin では `--code` 指定を推奨する。
   - `code` が既存なら GoTrue 発行前に die し、GoTrue orphan cleanup に頼らない。
6. `flag()` を値なし flag と値あり flag で扱い分ける。
   - `--dev` は値なしで true。
   - `--email --name foo` のように値が欠落した場合、次の flag を値として誤認しない。
7. `package.json`: `"provision:dev": "node scripts/provision.mjs --dev --compose-file infra/docker-compose.yml"`。
   利用は `pnpm provision:dev --email foo@example.com --code foo-admin`（stg/prod と同じく email/code は呼び出し時に付与）。
8. provision.mjs 冒頭コメントを 3 環境対応に更新（**N-5**: dev の固定 4 ユーザは `seed:gotrue:dev`、
   本スクリプト dev モードは ad-hoc admin 発行、という役割分担を相互リンクで明記）。
9. **N-4**: `provision:dev` は **CI / `dev:up` には組み込まない**（手動 ad-hoc 専用。固定ユーザは `seed:gotrue:dev` が担う）。

## 検証
- [ ] **B-1（実署名一致）**: `JWT_SECRET` 未 export の素の `dev:up` 状態で `pnpm provision:dev --email padmin@example.com --code padmin`
      → GoTrue 発行 + public.users 紐付け + 初期 PW 一度表示が成功し、**発行ユーザで login 200**（= provision の署名 secret と GoTrue 検証 secret が一致）
- [ ] 発行ユーザで `/me` `isAdmin:true`（admin として作られる）
- [ ] 重複: 同 email で再実行 → 「既に存在」で中止（GoTrue orphan を残さない）
- [ ] 重複: 既存 code（例: `--code admin`）で実行 → GoTrue 発行前に中止（dev seed の admin と衝突しない）
- [ ] **dev ガード**: `JWT_SECRET=not-dev pnpm provision:dev ...` は die（dev 値以外を拒否）
- [ ] **B-2（network フォールバック）**: `--dev` 無しで `--compose-file infra/docker-compose.yml` 直実行 → die
      （`waoon-stg` に刺さらない）。`--dev` + stg/prod compose の矛盾指定も die（N-2）
- [ ] **N-1**: dev で `--env-file` を併せて渡しても secret 判定は process.env 優先（dev は env ファイル無視）
- [ ] **stg/prod 回帰なし**: `provision:stg`/`prod` の挙動（dev 値 die ガード・network=waoon-stg/prod・env 必須）が不変
- [ ] 検証で作ったユーザは削除しクリーンに戻す

## リスク
| リスク | 影響 | 緩和 |
|---|---|---|
| dev 分岐追加で stg/prod のガードを緩めてしまう | 本番 secret 保護の後退 | dev は `--dev` 明示時のみ。stg/prod パスは現状コードを温存し分岐で隔離。検証で stg/prod ガード不変を確認 |
| dev モードが誤って stg/prod stack を叩く | 本番汚染 | dev は network=`waoon` + dev secret 必須（逆ガード）。stg/prod の secret では dev モードが die |
| dev seed 済みの `code=admin` と ad-hoc admin の既定 code が衝突する | GoTrue 作成後に DB insert が失敗し、provision が途中失敗に見える | `code` 既存チェックを GoTrue 発行前に追加。dev 検証・運用例では `--code padmin` のように一意 code を指定 |
| seed-gotrue-dev と役割が重複し混乱 | 運用の曖昧さ | 判断ログとコメントで「固定 4 ユーザ=seed:gotrue:dev / 任意 admin=provision:dev」を明記 |
