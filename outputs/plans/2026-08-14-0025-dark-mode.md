## 目的

アプリは実質ダーク未対応。テーマは `色(6) × 形(3) × 背景(9)` の 3 軸すべてが明色前提で、
色は JS で HSL 生成 → inline style 適用のため CSS 側から反転できない。

**反転境界を semantic トークン層に引く**ことで、catalog 部品とアプリ画面をまとめて反転させ、
ユーザーが light / dark / system を選べる状態にする。

## スコープ

### やること

- semantic トークンの dark 上書き（`[data-theme-mode="dark"]`）
- `body` 地色の semantic 化（現在 `var(--color-white)` 固定で反転しない）
- `colorScheme` 軸（light / dark / system）+ 永続化 + 切替 UI
- FOUC 対策（pre-paint inline script + `suppressHydrationWarning`）
- `design.ts` の inline 生成は**前景/neutral のコントラストのみ** dark 調整（ブランド色相は保持）
- app の **167 箇所 / 33 ファイル**のハードコード色を semantic トークンへ repoint

### やらないこと（スコープ外）

- **色生成ロジック（HSL 動的生成）そのものの作り直し**
- 新しい色テーマの追加・2 テーマ（business/modern）構想
- **WCAG AA 全面準拠**（下記「a11y の目標」参照。今回は目視 + 主要導線のみ確認）
- ダーク撮影の VRT 追加（4-dark）。[VRT Plan](2026-08-14-0020-vrt.md) 完了後の別作業

## 実装計画

親 Plan の三層モデルに沿い、**小さく landing してから広げる**。

1. **3a. semantic トークンの dark 上書き**（`feature/dark-tokens`・**単独 PR**）
   `tokens.css` の `--color-surface` / `--color-text-*` / `--color-border-*` / `--color-bg-*` を
   `[data-theme-mode="dark"]` で上書き。Tailwind v4 の
   `@custom-variant dark (&:where([data-theme-mode="dark"] *))` を配線する。
   **この PR 単独で、手動で属性を付けたときに catalog（DataTable 等）が反転すること**を検証してから次へ。
2. **3b. `body` 地色の semantic 化**（同 PR または直後）
   `var(--color-white)` → semantic surface トークンへ張替。167 箇所を触る前の土台。
3. **3c. colorScheme 軸 + FOUC 対策**（`feature/dark-toggle`）
   `infra/theme` に `colorSchemeAtom`（light/dark/system）+ storage。`ThemeSettingsModal` にトグル追加。
   `layout.tsx` の `<head>` に pre-paint inline script（localStorage + `matchMedia` を読み、
   paint 前に `<html>` へ `data-theme-mode` を付与）+ `<html suppressHydrationWarning>`。
4. **3d. `design.ts` の前景調整**（`feature/dark-inline-foreground`）
   `generateColorConfig(base, isDark)` で前景 / neutral のコントラストのみ dark 調整。
   ブランド色相は保持。`themeConfigAtom` の入力に colorScheme を足し inline のまま追従させる。
5. **3e-0. 対応表の作成**（実装前の設計ステップ・**完了**）
   下記「3e-0 対応表」を一次とする。
6. **3e. ハードコード色の repoint**（`feature/dark-repoint-*`・**画面群ごとに複数 PR**）
   対応表に従って置換する。`dark:` バリアントは semantic トークンが
   存在しない一点ものに限定する。PR は admin 系 / 回答系 / 認証系 / 共通コンポーネントで分割。

## 3e-0 対応表（2026-08-14 実測）

対象は apps/web の `*.tsx` / `*.ts` にある Tailwind の色ユーティリティ **167 箇所**
（`(text|bg|border)-<palette>-<step>` と `bg-white` / `text-white`）。

> 従来「143 箇所」としていたのは、`text-white` / `bg-orange-500` 等を拾わない狭い正規表現での
> 集計だった。以後は 167 を正とする。

### A. 用途も値も一致 — そのまま置換で light 不変（104 箇所 / 62%）

semantic トークンは gray スケールから作られているため、多くが**完全一致**する。

| `border-gray-200` | 9 | `--color-border-secondary` |
| `bg-gray-50` | 8 | `--color-bg-secondary` |
| `bg-white` | 8 | `--color-bg-primary` |
| `text-gray-600` | 8 | `--color-text-secondary` |
| `text-white` | 7 | `--color-text-inverse` |
| `bg-gray-100` | 4 | `--color-bg-tertiary` |
| `border-gray-300` | 4 | `--color-border-primary` |

| `bg-slate-50` | 2 | `--color-bg-subtle` |

### B. トークンを追加して light 不変にする（37 箇所）

同じ用途軸に一致する値が無いが、**トークンを足せば light を変えずに dark 対応できる**もの。
追加するのは 8 個。

| 用途 | 対象クラス | 件数 | 追加トークン（light → dark） |
|---|---|--:|---|
| リンク | `text-blue-600` 8 / `text-blue-700` 2 / `bg-blue-600` 1 | 11 | `--color-link` (#2563eb → #60a5fa) / `--color-link-hover` (#1d4ed8 → #93c5fd) |
| 成功 | `bg-green-500` 3 / `text-green-700` 3 / `bg-green-50` 1 | 7 | `--color-success` (#15803d → #4ade80) / `--color-success-bg` (#f0fdf4 → #14532d) |
| 警告 | `text-yellow-700` 3 / `bg-yellow-400` 2 / `bg-yellow-500` 1 / `text-orange-700` 1 / `bg-orange-500` 1 | 8 | `--color-warning` (#a16207 → #fbbf24) / `--color-warning-bg` (#fef3c7 → #78350f) |
| 反転面 | `bg-gray-900` 3 / `bg-gray-700` 2 / `bg-gray-400` 2 | 7 | `--color-surface-inverse` (#111827 → #e5e7eb) |
| エラー枠 | `border-red-300` | 4 | `--color-error-border` (#fca5a5 → #7f1d1d) |

**リンクはテーマ追従させない**（固定色として semantic 化する）。`--color-primary` に寄せると
6 色テーマの選択でリンク色が変わり、ダーク対応とは無関係な挙動変更が混入するため。

### C. light の見た目が変わることを許容する（20 箇所 / 12%）

gray の中間段は受け皿が無く、畳むと light も変わる。**ここだけが VRT で差分として出る想定**。

### D. 僅差で寄せる（6 箇所）

視認できない差なので、トークンを増やさず近傍へ寄せる。

| クラス | 件数 | 置換先 | 差 |
|---|--:|---|---|
| `text-slate-500` | 2 | `--color-text-muted` | `#64748b` → `#6b7280` |
| `border-gray-100` | 2 | `--color-border-light` | `#f3f4f6` → `#f1f5f9` |
| `bg-gray-200` | 2 | `--color-bg-tertiary` | `#e5e7eb` → `#f3f4f6` |

| 区分 | 件数 | light への影響 |
|---|--:|---|
| A. そのまま置換 | 104 | 変化なし |

## 検証

- **3a**: `<html data-theme-mode="dark">` を手で付けた状態で、**semantic トークンを参照している
  部品**（面・境界・テキスト）が反転する。`design.ts` の inline style 由来の色（ブランド色の塗り）は
  **3d まで据え置き**で反転しないのが正しい挙動 — この境界を目視で切り分けて確認する。
  light（属性なし）の見た目は**変わらない**
- **3b**: dark で地色が反転し、light で従来と同一
- **3c**: light / dark / system の切替が永続する（リロード後も保持）。
  **リロード時に明色フラッシュが出ない**（DevTools の低速 CPU で確認）。
  system 選択時に OS 設定の変更へ追従する
- **3d**: ブランド色（6 色テーマ）の色相が dark でも保たれ、前景のコントラストだけ改善する
- **3e**: 各 PR で light の差分を [VRT](2026-08-14-0020-vrt.md) の compare にかけ、
  **対応表の区分 C（20 箇所）に由来する差分だけを承認する**。
  A / B / D の箇所で差分が出たら事故として直す（差分ゼロが基準になるのは A / B / D）
- 全画面をダークで目視（コントラスト・破綻なし）
- 共通: `pnpm turbo run typecheck lint build test`

## リスク

| リスク | 対応 |
|---|---|
| **VRT の light baseline が間に合わない**（stg MinIO 待ち） | 3e を画面群ごとの小さい PR に割り、各 PR で before/after を手動比較する。VRT が使えるようになった時点で機械化へ切り替える |
| 色が 2 系統（A: `design.ts` inline / B: semantic トークン）+ 167 箇所の三層 | 反転境界を B に固定。A は前景のみ調整し、ブランド色相には触らない |
| **FOUC / hydration flash**（Jotai は hydration 後に確定） | pre-paint inline script + `suppressHydrationWarning`（3c）。低速 CPU での目視を検証項目にする |
| **背景テーマ 9 軸 × dark の組合せが 18 通り**になり目視が膨らむ | dark と背景軸は**直交**（背景の選択は保持し、前景/面だけ反転）。目視は代表 3 背景 × dark に絞り、残りは semantic トークン経由なので同挙動とみなす |
| 167 箇所の一括置換は差分が巨大でレビュー不能 | 画面群ごとに複数 PR。1 PR あたりの変更ファイルを 10 前後に抑える |
| semantic トークンに対応物が無い色があり `dark:` が乱発される | 対応物が無い場合は**まずトークンを足す**ことを検討し、`dark:` は一点ものに限定する。乱発を避けるため各 PR で `dark:` の追加数を記録する |
| `prefers-color-scheme` のデッドコードが生きて二重制御になる | 3a で `globals.css` の当該ブロックを**削除する**（二重制御の芽を残さない） |
| 追加する 8 トークンの dark 値が実物で破綻する（成功/警告/反転面は面の上で使われる） | 3e の該当 PR で目視確認する。特に `--color-success-bg` / `--color-warning-bg` は dark で暗色にするため、その上に載るテキスト（`--color-success` / `--color-warning`）とのコントラストを個別に見る |

## a11y の目標（提案）

今回は **WCAG AA 全面準拠を目標にしない**。理由は 167 箇所の置換と AA 監査を同時に走らせると
PR が肥大し、どちらも中途半端になるため。本 Plan では次に留める:

- 主要導線（ログイン / ダッシュボード / 回答フロー / admin 一覧）のテキストコントラストを
  dark で目視確認する
- 明らかに読めない箇所はその場で直す
- AA の網羅監査は別 Plan に切り出す
